# Notification Service — заметки по разбору проекта

Конспект по проекту notification-service: разбор маршрута отправки уведомлений,
работа с Redis и концепция батчей.

---

## 1. Маршрут `POST /api/notifications/send` пошагово

Маршрут: `Route::post('/notifications/send', [NotificationController::class, 'send'])`.

### Шаг 0. До входа в контроллер

Маршрут объявлен в `routes/api.php` и попадает в группу `api`
(`app/Http/Kernel.php`): туда входит `throttle:api` (rate limiting) и
`SubstituteBindings`. CSRF для api не проверяется.

Про rate limiting: лимитер `api` определён в `RouteServiceProvider::boot()` —
60 запросов в минуту на IP (или на id пользователя, если он авторизован).
Счётчики лимитера хранит **default cache store**, а он у нас `file`
(`config/cache.php`, `CACHE_DRIVER` в `.env` не задан). То есть сейчас лимит
запросов пишется в файлы (`storage/framework/cache/data`), а **не в Redis**.
Redis задействовался бы только если задать `CACHE_DRIVER=redis` в `.env`.

### Шаг 1. Валидация — `SendNotificationRequest`

Laravel автоматически прогоняет запрос через `FormRequest`:

- `channel` — обязателен, `in:sms,email`
- `message` — обязателен, строка до 1000 символов
- `recipient_ids` — массив 1–1000 элементов
- `priority` — опционально `high|low` (по умолчанию `low`)
- `idempotency_key` — опционально

### Шаг 2. Контроллер

`NotificationController::send` берёт провалидированные данные и вызывает
`NotificationService::sendBulk(...)`, затем отвечает `202 Accepted` с `batch_id`.

### Шаг 3. `NotificationService::sendBulk` — ядро (здесь и живёт Redis)

**3.1. Подготовка**

```php
$batchId   = Str::uuid();                          // id всей рассылки
$queueName = $priority === "high" ? "high_priority" : "marketing";
```

Очередь RabbitMQ выбирается по приоритету (не по каналу).

**3.2. Быстрый путь через Redis (проверка, не бронь)**

Для **каждого получателя**:

```php
$key      = $idempotencyKey ?? "{$batchId}:{$recipientId}";
$redisKey = "idempotent:{$key}";

// Быстрый путь: ключ уже обработан ранее → пропускаем без обращения к БД
if (Redis::get($redisKey)) {
    $skippedCount++;
    continue;
}
```

Redis-ключ `idempotent:{key}` — это **кэш-маркер** «ключ уже обработан», а не
замок. Он ставится **только после успешной вставки в БД** (см. 3.3), поэтому
«зависших» маркеров без записей не бывает: упала БД → маркер не ставился →
повторный запрос пройдёт нормально. TTL — 24 часа.

**3.3. Запись в БД: БД — источник правды, дубли отсекает unique-индекс**

```php
DB::transaction(function () use (...) {
    foreach (array_chunk($records, 100) as $chunk) {
        DB::table("notifications")->insertOrIgnore($chunk);  // ON CONFLICT DO NOTHING

        // только строки, вставленные этим запросом (id генерируем сами)
        $ours = Notification::whereIn("id", array_column($chunk, "id"))
            ->pluck("id", "idempotency_key");

        foreach ($ours as $key => $notificationId) {
            $inserted[$key] = $notificationId;
        }

        // строки, не вставленные из-за конфликта по ключу → пропущены
        $skippedCount += count($chunk) - count($ours);
    }

    // Redis-маркеры, батч-сет и джобы — только ПОСЛЕ коммита
    DB::afterCommit(function () use ($inserted, $batchId, $queueName) {
        foreach ($inserted as $key => $notificationId) {
            Redis::set("idempotent:{$key}", "1", "EX", self::IDEMPOTENCY_TTL);
            Redis::sadd("batch:{$batchId}:ids", $notificationId);
            SendNotificationJob::dispatch($notificationId, $queueName);
        }
        Redis::expire("batch:{$batchId}:ids", 3600);
    });
});
```

- `insertOrIgnore` генерирует `INSERT ... ON CONFLICT DO NOTHING` — дубли
  отсекаются **атомарно** на уровне unique-индекса `idempotency_key`, без
  исключений и без гонок.
- Всё посторитое с Redis (маркеры, `SADD`, dispatch) выполняется в
  `DB::afterCommit()`: если транзакция откатится — ничего из этого не
  произойдёт. Так закрывается dual-write между Redis и БД.
- Джобы дополнительно защищены `after_commit => true` в конфиге rabbitmq
  (`config/queue.php`).

**3.4. Отдельной ветки на гонку больше нет**

Раньше при `QueryException` с кодом `23505` была recovery-ветка с повторной
вставкой недостающих записей. Теперь она не нужна: `ON CONFLICT DO NOTHING` не
бросает исключений — конфликт просто пропускается и учитывается в `skipped`.

Схема идемпотентности теперь одноуровневая и транзакционная:

```
Redis::get (fast-path, кэш) → miss → INSERT ... ON CONFLICT DO NOTHING (БД, атомарно)
                                  ↑ дубль отсекается здесь, без исключений
→ успешно вставленные → Redis-маркер + SADD + dispatch (только после коммита)
```

### Шаг 4. Фоновая обработка — `SendNotificationJob` (в worker'е, RabbitMQ)

**4.1. `handle(GatewayService $gateway)`**

- Находит уведомление; если статус уже не `queued` — пропуск (защита от
  повторной обработки).
- Дёргает `GatewayService::send()` — имитация провайдера (10% сбоев).
- Успех → статус `delivered`, `delivered_at`, `provider_message_id`.
- Сбой → retry с нарастающей задержкой (`release(60 * retry)`), до 3 попыток;
  исчерпал → статус `failed` + DLQ.

**4.2. DLQ через Redis (третье применение Redis)**

```php
Redis::pipeline(function ($pipe) use ($dlqEntry) {
    $pipe->lpush("dlq:notifications", $dlqEntry);
    $pipe->ltrim("dlq:notifications", 0, 9999);   // ограничение 10 000 записей
});
```

- Redis **List** используется как dead-letter queue: `LPUSH` записи с полными
  данными уведомления и ошибкой, `LTRIM` — обрезка по размеру. Читается командой
  `php artisan dlq:show`.

### Итог: где именно используется Redis в этом сценарии

| Ключ | Тип | Команды | Назначение |
|---|---|---|---|
| `idempotent:{key}` | string | `GET` (fast-path), `SET EX` (маркер после вставки) | Дедупликация запросов (маркер на 24 ч) |
| `batch:{batchId}:ids` | set | `SADD`, `EXPIRE` | Трекинг членов батча (TTL 1 ч) |
| `dlq:notifications` | list | `LPUSH`, `LTRIM`, `LLEN` | Dead-letter очередь неудавшихся уведомлений |

Примечание: `throttle:api` (rate limiting) в текущей конфигурации Redis **не
использует** — счётчики лимита живут в default cache store (`file`, т.к.
`CACHE_DRIVER` не задан). Redis подключился бы к rate limiting только при
`CACHE_DRIVER=redis`.

**Важные нюансы архитектуры:**

1. Идемпотентность решается **на уровне БД** (unique-индекс + `ON CONFLICT DO
   NOTHING`) — атомарно и транзакционно. Redis-маркер `idempotent:{key}` — лишь
   кэш-fast-path, он ставится только после успешной вставки, поэтому маркер без
   записи существовать не может.
2. Маркеры живут 24 часа (TTL) и не снимаются после успеха — повторный вызов с
   тем же ключом вернёт 202 с `created=0`.
3. Redis-записи (`SET`, `SADD`, `EXPIRE`) и dispatch джобов выполняются в
   `DB::afterCommit()` (плюс `after_commit => true` для rabbitmq) — при откате
   транзакции ничего из этого не происходит.
4. Батч-ключи `batch:*` и DLQ имеют TTL/лимиты, так что Redis не засоряется
   бесконечно.

## 2. Что делают методы Redis в этом контексте

### 1. `Redis::set($redisKey, "1", "EX", self::IDEMPOTENCY_TTL, "NX")`

**Генерируемая Redis-команда:**

```
SET idempotent:{key} 1 EX 86400
```

**Что делает:** записывает ключ с TTL (24 часа). Используется как **маркер**
«этот idempotency_key уже обработан», а не как замок: он ставится **только
после** успешной вставки записи в БД (в `DB::afterCommit`).

**Возвращает:** `true` при успешной записи, `false` при ошибке.

**В контексте проекта** — маркер на каждого получателя:

```php
// fast-path при новом запросе:
if (Redis::get($redisKey)) { $skippedCount++; continue; }

// ...после успешной вставки в БД (в afterCommit):
Redis::set($redisKey, "1", "EX", self::IDEMPOTENCY_TTL);
```

- первый запрос с ключом `user1` → вставка в БД прошла → маркер записан;
- повторный запрос с тем же ключом → `Redis::get` вернул `1` → получатель
  пропускается, дубль не создаётся (даже если бы fast-path промахнулся, дубль
  отсечёт unique-индекс БД);
- через 24 часа ключ сам исчезнет, и тот же ключ снова можно будет использовать.

⚠️ Если Redis упал в момент `afterCommit` — маркер не поставится, но запись в БД
уже есть; повторный запрос просто попадёт в `ON CONFLICT DO NOTHING` и будет
корректно пропущен (расхождение закрывает БД).

### 2. `Redis::sadd("batch:{$batchId}:ids", $notificationId)`

**Команда:**

```
SADD batch:550e8400-...:ids 7f3c1a2b-...
```

**Что делает:** добавляет элемент в Redis **Set** (неупорядоченное множество
уникальных значений).

**Возвращает:** `1`, если элемент добавлен, `0`, если он уже был в множестве.

**В контексте проекта** — ведёт «реестр» батча: после вставки в БД каждый реально
созданный id уведомления кладётся в set `batch:{batchId}:ids`. По этому ключу
можно узнать: сколько уведомлений реально создано в батче (`SCARD`), какие именно
(`SMEMBERS`), отслеживать прогресс обработки (сверять со статусами в БД).

Внимание: `sadd` вызывается **внутри** транзакции БД, т.е. set наполняется
параллельно с коммитом записей.

### 3. `Redis::expire("batch:{$batchId}:ids", 3600)`

**Команда:**

```
EXPIRE batch:550e8400-...:ids 3600
```

**Что делает:** устанавливает время жизни ключа — 3600 секунд (1 час).

**Возвращает:** `1`, если TTL установлен, `0` — если ключа не существует.

**В контексте проекта** — «страховка от мусора»: set `batch:*` нужен только пока
батч актуален (обработка + возможный анализ). Через час ключ удалится
автоматически, и Redis не засорится навсегда сотнями батчей. Без этого `SADD`-ы
копились бы бесконечно.

### 4. `Redis::pipeline(...)` — это не одна команда, а группировка

```php
Redis::pipeline(function ($pipe) use ($dlqEntry) {
    $pipe->lpush(self::DLQ_REDIS_KEY, $dlqEntry);
    $pipe->ltrim(self::DLQ_REDIS_KEY, 0, self::DLQ_MAX_SIZE - 1);
});
```

**Что делает pipeline:** отправляет все команды из замыкания **одним пакетом** в
Redis (один round-trip по сети вместо двух), и исполняются они последовательно
без вмешательства других запросов. Это и быстрее, и атомарнее для пары «добавил →
обрезал».

**4a. `LPUSH dlq:notifications {json}`**

```
LPUSH dlq:notifications {"notification_id":"...","error":"..."}
```

Добавляет элемент **в начало** Redis **List**. В проекте туда кладётся JSON с
данными уведомления и ошибкой → список ведёт себя как dead-letter queue: самые
свежие ошибки — в начале (`LRANGE dlq:notifications 0 9` покажет последние).

**4b. `LTRIM dlq:notifications 0 9999`**

```
LTRIM dlq:notifications 0 9999
```

Оставляет в списке только элементы с индексами от 0 до 9999 (т.е. **первые
10 000**), всё остальное с конца — удаляет. Это «шляпа ограниченного размера»:
очередь не растёт бесконечно, старые записи вытесняются новыми.

**В контексте проекта** — оба вызова вместе: уведомление, исчерпавшее все попытки
доставки (или упавшее с исключением), попадает в DLQ, и очередь гарантированно не
превышает 10 000 записей. Дальше её разбирают вручную (`php artisan dlq:show`).

### 5. `Redis::llen(self::DLQ_REDIS_KEY)`

**Команда:**

```
LLEN dlq:notifications
```

**Что делает:** возвращает **количество элементов** в списке (длину).

**Возвращает:** целое число — текущий размер списка.

**В контексте проекта** — логирование размера DLQ после добавления записи:

```php
Log::info("Notification pushed to DLQ", [
    "dlq_size" => Redis::llen(self::DLQ_REDIS_KEY),
]);
```

Если `dlq_size` растёт — значит, провайдер/шлюз систематически недоступен.

### Сводная таблица

| Вызов | Команда Redis | Тип данных | Возврат | Роль в проекте |
|---|---|---|---|---|
| `Redis::get(...)` / `Redis::set(...,"EX",...)` | `GET` / `SET EX` | string | `1`/`null` | fast-path проверка + маркер идемпотентности (TTL 24 ч, ставится после вставки в БД) |
| `Redis::sadd(...)` | `SADD` | set | 1/0 | реестр id батча |
| `Redis::expire(...,3600)` | `EXPIRE` | — | 1/0 | TTL для set батча |
| `Redis::pipeline` | пакет команд | — | массив результатов | атомарная группировка LPUSH+LTRIM |
| `$pipe->lpush(...)` | `LPUSH` | list | длина после push | запись в DLQ |
| `$pipe->ltrim(...,0,9999)` | `LTRIM` | list | `OK` | ограничение DLQ 10 000 записями |
| `Redis::llen(...)` | `LLEN` | list | int | размер DLQ для логов |

## 3. Что такое «батчи» и зачем они нужны

**Батч = одна логическая рассылка, созданная одним HTTP-запросом.**

Когда клиент шлёт `POST /api/notifications/send` с массивом получателей:

```json
{
  "channel": "sms",
  "message": "Акция!",
  "recipient_ids": ["user1", "user2", "user3"],
  "priority": "high"
}
```

- сервис генерирует один `batch_id` (UUID) на **весь запрос**;
- внутри одного батча создаётся **N отдельных записей** в таблице `notifications`
  (по одной на получателя);
- каждому получателю уходит **отдельный job** в очередь.

Иерархия:

```
Batch (batch_id, 1 шт.)          ← уровень «рассылки»
 ├── Notification (user1, id 1)  ← уровень «получателя»
 ├── Notification (user2, id 2)
 └── Notification (user3, id 3)
```

### Зачем это нужно

#### 1. Связывание разрозненных записей в одну операцию

Каждая запись в БД — независимая строка, но по `batch_id` (точнее по Redis-set
`batch:{batchId}:ids`) можно сказать: «вот эти 3 уведомления — это одна рассылка
от 12:00». Клиент получает `batch_id` в ответе (202) и может по нему ссылаться на
всю отправку целиком, а не на каждое уведомление отдельно.

#### 2. Дедупликация внутри батча (связь с идемпотентностью)

Если клиент не передал `idempotency_key`, сервис сам генерирует его на основе
батча:

```php
$key = $idempotencyKey ?? "{$batchId}:{$recipientId}";
```

Ключ `{batchId}:{recipientId}` уникален для пары «рассылка + получатель». Поэтому
**повторная отправка того же запроса** (например, из-за ретрая клиента или
двойного клика) не создаст дубли: для каждого получателя `SET ... NX` уже занят →
все получатели попадут в `skipped`, и в БД ничего нового не появится. Ответ всё
равно вернётся 202, но с пустым батчем.

#### 3. Трекинг батча через Redis

```php
Redis::sadd("batch:{$batchId}:ids", $notificationId);
Redis::expire("batch:{$batchId}:ids", 3600);
```

Set `batch:{batchId}:ids` — «реестр участников» батча в Redis: какие id
уведомлений реально созданы. Он нужен, чтобы быстро отвечать на вопросы «сколько
уведомлений в этой рассылке / какие именно» без запроса к БД (или в дополнение к
нему), и для потенциальной отчётности о прогрессе.

#### 4. Батч — единица для аналитики и отчётов

Если уведомление «доставлено» — это статус строки; если «рассылка прошла
наполовину» (2 из 3 доставлено) — это уже статистика **уровня батча**. Батч
позволяет строить сводки вида «сколько отправок провалилось полностью».

### Важный нюанс (честно про текущий код)

Ключи `batch:*` сейчас **только пишутся, но нигде не читаются**:

- `Redis::sadd("batch:...:ids", ...)` — пишем,
- `Redis::expire(..., 3600)` — ставим TTL,
- но **нет ни одного места**, которое делало бы `SMEMBERS`/`SCARD` по этим
  ключам, и нет эндпоинта вида `GET /api/batches/{id}`.

То есть это **задел на будущее**: инфраструктура для отслеживания батчей
(прогресс, отчёт, retry всего батча) уже заложена, но пока не имеет потребителя.
Сами батчи при этом уже выполняют две реальные задачи прямо сейчас: группировка
записей через `batch_id` в ответе и генерация ключей идемпотентности
`{batchId}:{recipientId}`.

TTL 3600 не случайность: батч считается «живым» в Redis час — достаточно, чтобы
обработать все джобы и (в будущем) дать клиенту спросить статус, после чего ключ
сам очистится.
